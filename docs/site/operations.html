Operations

How to configure a Goose Web server, run it behind a proxy, and what to expect from it under load.

Configuration

web::server_config() returns the defaults. Set fields before web::run; validate_server_config rejects bad combinations before any socket opens. The most used fields:

FieldDefaultMeaning
port80801 to 65535
public_bindfalsefalse binds 127.0.0.1; true binds all IPv4 addresses
max_clients64open connections, at most 64
max_request_bytes8192headers and body of one request
max_response_bytes1048576one response body; up to 16 MiB
max_pool_bytes8388608serialized responses in flight, shared by all connections
read_timeout_ms, write_timeout_ms5000time to receive a request once it starts; time to write one response
idle_timeout_ms5000wait for the next request on a kept-alive connection
keep_alive, max_requests_per_connectiontrue, 100connection reuse and its limit
shutdown_grace_ms5000how long shutdown waits for open connections
handle_signalsfalsestop on SIGINT and SIGTERM with a drain
max_sse_clients, sse_heartbeat_ms32, 15000open event streams, and their heartbeat interval

The full table, with valid ranges, is in the API reference.

Command line and environment

web::config_from_args(args()) reads the common options, and web::config_from_env() reads two environment variables. Unknown options are errors, so typos fail at startup.

ArgumentEnvironmentEffect
[port], --port NGOOSE_WEB_PORTthe listening port
--host public or --host loopbackGOOSE_WEB_PUBLIC=1 or 0all IPv4 addresses, or loopback only
--max-clients Nnoneconnection limit, 1 to 64
--max-requests Nnonestop after N completed responses; 0 means no limit

An application that takes its own positional arguments passes only the prefix it owns to config_from_args and reads the rest itself, as the basic example does.

Deployment

Bind and expose

The default is loopback. Use --host public only when the process should accept connections from other machines, and put it behind something you trust.

Behind a reverse proxy

  • TLS belongs to the proxy. Goose Web does not speak TLS yet. Serve HTTPS at the proxy, and set secure = true on session cookies and Strict-Transport-Security through secure_headers.
  • The client address is the proxy's until you say otherwise. c.peer() is the TCP peer, and forwarded headers are ignored by default, so a rate_limit behind a proxy limits the proxy. Add trust_proxies(c, web::trusted_proxies("10.0.0.0/8")) with the proxy's own addresses (IPv4, IPv6 or CIDR, up to 16) and client_ip(c) returns the first untrusted address on X-Forwarded-For (or RFC 7239 Forwarded with cfg.forwarded = true). Trust only proxies you run: a trusted peer's headers are believed. Requests from other peers never change the address, however they are sent.
  • Sessions are stateless. Every instance that should accept a session needs the same secret. Rotating the secret signs every user out.
  • Limits are per process. Rate limits, event streams and the response pool are not shared between instances.

Running and stopping

Set handle_signals so SIGTERM from a supervisor starts a drain: the listener closes, open requests finish, and streams receive their close event. Keep the grace period longer than your slowest handler. The logger middleware prints one line per response to standard output, so a supervisor or log shipper can collect it directly.

Request logs

For a log pipeline, use json_logger instead: one JSON object per line on standard output, with ts (RFC 3339 UTC), level, request_id, method, path (no query string unless you pass include_query), route (the pattern, such as /users/:id), status, bytes, duration_us, peer, client_ip, a truncated user_agent, and pid in worker processes. Values are escaped, so a crafted request cannot break a line. Keep the query string out of logs unless you need it: it can carry tokens.

{"ts":"2026-10-24T10:15:03Z","level":"info","request_id":12,"method":"GET","path":"/users/42","route":"/users/:id","status":200,"bytes":9,"duration_us":84,"peer":"127.0.0.1","client_ip":"127.0.0.1","user_agent":"curl/8.7.1"}

Overload

Put shed_load on the routes that can be shed. Above the configured share of open connections or response-pool bytes, the server answers 503 overloaded with Retry-After and the handler does not run. Pressure is per worker process. Each route can also cap its body with body_limit, and etag lets clients skip unchanged responses with If-None-Match.

Several processes

Set workers (or pass --workers N, or GOOSE_WEB_WORKERS) to pre-fork that many reactor processes on one port; 0 means one per CPU. The parent owns the listener and signals, restarts a worker that crashes, drains all of them on SIGTERM and sums their stats. On a 16-core development box the hello example served about 129k requests/s with one worker and about 395k with four (keep-alive load, two local load generators).

./build/server --port 8080 --workers 4

Each worker has its own copy of the program's globals: in-memory stores, sessions, rate-limit counters and server-sent event streams are per worker. Keep shared state in SQLite (each worker opens its own connection after the fork) or another external store. Details are in the API reference.

Performance notes

Each Goose Web process is single-threaded: one readiness loop accepts, reads, runs handlers and writes. Memory is bounded by the configuration of each process. Some properties to design around:

  • Handlers run on the reactor. Work that blocks (a slow file, a long SQLite query, a network call made synchronously) delays every other connection in that process. Keep handlers short.
  • SQLite calls block. Index the columns you filter on, keep select loops short, and cap list sizes with limit. Worker offload is planned for the asynchronous milestone, not available now.
  • Static files are read whole. A file is read on the reactor, bounded by max_response_bytes, so serve small assets from the framework and large ones from a proxy or CDN.
  • Responses are bounded. A body over the limit is a complete 500, and a response that does not fit the pool gets a 503 and its connection closes. Both are visible failures, not silent truncation.
  • Connections are bounded. Up to 64 at once, with read, write and idle deadlines. A slow client is closed when its deadline passes rather than holding a slot.
  • Event streams drop slow readers. A stream more than 256 KiB behind is closed and counted, so one slow browser cannot hold up the others.
No benchmark results are published yet. The roadmap lists benchmarks for slow clients, queue saturation and memory bounds as part of the asynchronous work. Measure your own handlers before sizing a deployment.
